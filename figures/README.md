## How the published figures were produced

Each figure is made in two steps, and we state the division because only the first is
script-generated.

1. **Panels** are produced by the notebooks and scripts listed above, from the deposited data
   and the flat tables in `plotdata/`. Everything that carries a number - axes, data points,
   colour scales, band structures, fatbands - comes from this step and is fully reproducible.
2. **Final assembly** - arranging the panels, panel lettering, annotation arrows, and the
   schematic elements - was done in presentation software for the published version. That
   step changed layout and labelling only; it did not alter any plotted value. It now has
   generating code too: `compose_figures.py` rebuilds Figs. 3, 4, 5 and SI S5-S6 from the
   panels and the structure images, at the published page size and geometry.

Figure 1 is entirely a schematic and has no generating code at all.

A reader who wants to check a number should go to step 1: run the notebook or script for that
panel, or read the corresponding table in `plotdata/`. The published PDF differs from the
script output in layout and lettering, not in content.

## Two changes were made — the originals are kept unmodified in `archive/`

**1. The SHAP values were hard-coded.** The original `shap_bar_original.ipynb` writes the three
numbers in directly:

```python
shap_values = [0.0328, 0.0359, 0.1122]   # p/d, MPF, MSBI  (eV)
```

They had been computed in a different notebook and copied across, so the figure could not be
reproduced from the plotting code alone. `plot_shap_bar.py` instead reads `shap_rank.csv`,
which `shap_recompute.py` generates.

**2. The log1p → eV conversion was removed.** The original pipeline
(`archive/KPS_DFT_free_BO_SGK_original.ipynb`) multiplies the SHAP values in the training space
by a local-linearization factor to convert them to eV:

```python
if TRANSFORM_KIND == 'log1p':
    scale = np.exp(z_pred)                     # d(expm1(z))/dz
if TRANSFORM_KIND == 'log1p' and USE_SMEARING:
    scale = c_cv_final * scale                 # empirical smearing correction
shap_sse_run = shap_z * scale.reshape(-1, 1)
```

The additivity of Shapley values holds in the **model output space** and does not survive a
non-linear inverse transform. The revision reports mean|SHAP| in the log1p space directly.

The original SHAP values were also computed **in-sample** on a model fitted to all rows and
averaged over 100 seeds. `shap_recompute.py` computes TreeSHAP **only on the held-out folds**
of a parent-grouped `GroupKFold(5)` and averages over 20 seeds. Those two changes — the space,
and in-sample → held-out — account for the difference between the manuscript's top-three total
of 37.4 % and the revised 42.0 %.

## What each panel of `redraw_figures_R1.ipynb` can be tuned with

The presentation choices are named constants rather than scattered literals, so a panel can be
adjusted without reading the plotting code. Every one of them is local to its cell except
`DPI`, which lives in the setup cell.

| Constant | Cell | Default | Effect |
|---|---|---|---|
| `DPI`, `DPI_DEFAULT` | setup | `figure2: 1000`, others `800` | **PNG** resolution |
| `PNG_DPI`, `PDF_RASTER_DPI` | `reference_plots/_save.py` | `800` / `400` | the same two-tier policy for the scripts in `reference_plots/` |
| `PDF_RASTER_DPI` | setup | `400` | resolution of the **rasterized layers inside the PDF** - the point clouds. Text, axes and lines stay vector whatever this is. This is the single biggest lever on memory (see below) |
| `PNG_MAX_MPIX` | setup | `200` | caps the PNG side. A 13 x 7.2 in canvas at 1000 dpi is 94 Mpx, about 0.4 GB per buffer; past the cap the PNG dpi is reduced rather than risking the OS killing the process, which it does before Python can catch anything. The PDF is unaffected |
| `FONT_DIRS`, `$TIMES_FONT_DIR` | setup | usual font locations | see **Fonts** below |
| `NAME_X` | Fig. 2 | `0.5` | where the feature names sit across the gutter between panels (a) and (b): `0.0` flush against (a), `0.5` midway, `1.0` flush against (b), which is matplotlib's default right-aligned tick label. The gutter width is measured from the real axes positions after the colorbar has taken its share, so the fraction survives changes to `figsize`, `width_ratios` and `wspace` |
| `BAR_VALUES`, `BAR_VALUE_FMT`, `BAR_VALUE_FS` | Fig. 2 | `True`, `'{:.4f}'`, `FS_TICK` | the mean\|SHAP\| value written on each bar of panel (a), in the same format as the Table 1 rows. | `FS3_SCALE` | Fig. 3 | `1.2` | scales every piece of text in the a-c stack - axis labels, ticks, colorbar label and ticks, the CuO/FeSi call-outs - relative to the shared `FS_*` sizes. `1.0` is the published size; `1.2` is what puts a-c on the same type size as the band panels beside it (see below). The panel letters are not scaled with it - `PANEL_PT` is set so they land at the composite's 20 pt |
| `FS4_SCALE` | Fig. 4a | `1.54` | the same, for Fig. 4a |
| `PT_SCALE` | Fig. 4a | `1.0` | marker **diameter** scale. matplotlib's `s` is an area, so the code squares it. 1.0 is the published size |

### Matching the published text size and panel shape

`FS_SCALE = 1.0` gives the *nominal* published point sizes, but a figure drawn on a wider
canvas than the published one then carries text that is too small for its panel. Both were
measured off the published PDFs rather than guessed - text height in points from
`pdftotext -bbox`, panel geometry from the axes rectangle in a 200 dpi render - and the
scales and canvases set from that:

The panel rectangle is measured one panel at a time. Measuring the a-c stack as a single
block, as a first pass did, gives the height of the whole column including the gutters
between panels, and matching *that* leaves the individual panels the wrong shape. It also
mislabels Fig. 4: the near-square 3.975 x 3.920 in box in that figure is panel **b**, not
panel a, and matching 0.98 made Fig. 4a square when the published panel is 1.27 wide-to-tall.

| | published | here |
|---|---|---|
| Fig. 2, aspect of the cropped page | 1.555 | 1.567 |
| Fig. 3a-c, each panel | 2.765 x 2.16 in (1.279) | 2.795 x 2.190 in (1.276) |
| Fig. 3a-c, axis label | 16.61 pt | 16.64 pt at `FS3_SCALE = 1.0`, 19.97 at 1.2 |
| Fig. 4a, panel | 3.900 x 3.070 in (1.270) | 3.915 x 3.095 in (1.265) |
| Fig. 4a, colorbar label | 40.10 pt | 40.06 pt |

So Fig. 2 is drawn 13.0 x 7.55 in (aspect only - its text was already right), Fig. 3a-c
3.85 x 10.69 in, and Fig. 4a 5.40 x 4.02 in at `FS4_SCALE = 1.54`.
At the published panel width the shared `FS_*` sizes already give the published text, which
is why Fig. 3 needs no scaling at all once its canvas is right.

The other scales are at 1.0, the published size.

**Fig. 3a-c is at 1.2, not 1.0, and the reason is the composite.** Its three panels sit
beside the CuO and FeSi band panels, which are drawn by different code at their own sizes,
and at the published sizes the two halves of one figure carried noticeably different type -
tick labels 13.6 pt against 16.5. `FS3_SCALE = 1.2` closes that: measured on the composed
page, a-c now reads 16.38 pt against the band panels' 16.11.

Raising it does not shrink the plots. The a-c canvas is 3.85 x 10.69 in with the three axes
placed explicitly, so the larger type grows the margins instead of eating into the boxes:
each panel is 2.795 x 2.195 in either way, against the published 2.765 x 2.160. What changes
is the page, 322.2 x 674.9 pt at 1.0 and 332.2 x 679.0 at 1.2 - which is why `figure3()` in
`compose_figures.py` reads that page size out of the file rather than carrying it as a
constant. A stale constant there would not fail; it would silently stretch the column by the
difference, because the column is placed on a rectangle.

Five further details were measured off the published figures and matched rather than left
to matplotlib's defaults:

| | published | now |
|---|---|---|
| Fig. 3 colorbars | numbers only, no axis label | no label |
| Fig. 3a x ticks | every decade | `LogLocator(numticks=20)` |
| Fig. 3a colour limit | ±0.30 | 0.30 |
| Fig. 3c x ticks | 0.1 / 0.5 / 1 / 2 | same |
| Fig. 3 and 4a y ticks | every 0.2 | pinned to 0.0 ... 1.6 |
| Fig. 4a colormap | **`rainbow`** | `rainbow` |

The colormap is the one that would be easiest to get wrong. Sampling the published Fig. 4a
colorbar down its length gives (91, 12, 198) at the foot - the violet `rainbow` starts on -
where `jet`, which the notebook had been using, starts at navy (0, 0, 127). Fitting the
whole ramp against eight candidate colormaps picks `rainbow` outright. Raising one does not just enlarge the
glyphs, so the layout is gated on it: past `FS3_SCALE > 1.3` (`BIG3`) the Fig. 3 colorbar
label is broken over two lines because it no longer fits along the panel height, its y ticks
are pinned to `0.0 / 0.5 / 1.0 / 1.5` which matplotlib otherwise thins to `0 / 1`, and the
gutters grow; past `FS4_SCALE > 1.3` (`BIG4`) the Fig. 4a abscissa labels every 1.0 Å instead
of 0.5 Å and keeps the 0.5 Å positions as unlabelled minor ticks, because at that size the
labels collide.

Fig. 3 also carries explicit decade sub-ticks (`LogLocator(subs=2..9, numticks=100)`). Panels
(a) and (b) span six and three decades, and over that range matplotlib's automatic minor
locator returns no ticks at all, which left the logarithmic abscissa of panel (a) unmarked.

### Which point clouds are rasterized, and why it is not one rule

`rasterized=True` on a scatter is not a free choice - both settings have a failure mode, and
each cloud here was set from which one it hits.

**A single-colour rasterized layer is written wrong.** matplotlib hands the PDF backend an
RGBA buffer; if its RGB side holds one colour, the backend writes a 1-bit indexed image with
a soft mask carrying the alpha, and viewers render that with pale diagonal seams across the
cloud. The PNG of the same figure is clean, so it only shows in the PDF.

**A large vector cloud is written correctly but is unusable.** SI Fig. S4's 99,960 trials
became 100,016 drawing operations, which several viewers take tens of seconds to render or
give up on entirely - the symptom that made us look.

So:

| Cloud | Points | Setting |
|---|---:|---|
| SI S3, parity scatter | 3,845 | vector - small enough, and single-colour |
| Fig. 4b, the two `p/d` populations | 3,845 | vector |
| SI S4, trial cloud + best-so-far line | 99,960 | **rasterized together**, `set_rasterization_zorder(2.5)` |

SI S4 is the interesting one: rasterizing the black cloud alone would hit the first failure
mode, so the blue best-so-far line goes into the same rasterized layer. Two colours in one
buffer is enough for the backend to write an ordinary 8-bit RGB image with no soft mask. The
red new-best markers sit above the zorder threshold and stay vector, as do the axes, the
frame and every piece of text. 100,016 drawing operations become 37.

## Assembling the published composites — `compose_figures.py`

Figs. 3, 4, 5 and SI Figs. S5–S6 are composites: plotted panels beside crystal-structure
renderings, arranged in presentation software for the manuscript. `compose_figures.py` does
that arrangement in code, so the whole figure is reproducible rather than only its plotted
halves.

```bash
python figures/compose_figures.py                 # all five -> figures/composed/
python figures/compose_figures.py --only 5 S5 S6
```

Every plotted panel is placed with `show_pdf_page` or `insert_image` from `Figures_R1/`;
nothing is re-rendered and nothing vector is rasterized. The geometry is measured off the
published PDFs rather than guessed — text origins from the PDF text layer, axes and image
rectangles from a 200 dpi render and `page.get_image_info()`, and each structure's target
rectangle from where its ink actually starts and stops inside the published image, so a
replacement crop with a different margin still lands at the published size.

Two details are worth knowing:

* **`H_σ`**, which labels the spin colorbars on Figs. 4 and 5 and SI S5–S6, is an italic H
  with an italic σ subscript, 24.0 pt over 17.5 pt, set in **Cambria Math** — a Microsoft
  font that is not in this repository. It does not have to be: the published PDFs embed a
  subset of it, so the composites use the published figures' own copy.

  The subset cannot be used as it stands. It is a Type0 font with Identity-H encoding, whose
  glyphs are addressed by glyph id, and its `cmap` carries only the six code points the
  published pages happened to need. `H` and `σ` are not among them — the published label uses
  the mathematical alphanumerics U+1D43B and U+1D70E — so PyMuPDF draws a blank for the σ.
  The font's own `ToUnicode` map says which glyph is which, and under Identity-H the code
  *is* the glyph id, so `cambria_math()` adds those two glyphs to the `cmap` at `H` and `σ`
  and the font then behaves like any other. If the published PDF or fontTools is missing,
  `h_sigma()` falls back to Times New Roman Italic at sizes matched to the published glyphs'
  ink boxes, and says so.
* **Structure images.** `figures/structures/` holds one PNG per compound and is what the
  composites use; see its README. `crop_structures.py` crops all ten:

  ```bash
  python figures/crop_structures.py              # all ten
  ```

  The six with a VESTA export in `final_structure/` are cropped out of it — a 4130 x 1995
  canvas with the structure in the middle and the a/b/c axis triad off to the left. CuO,
  FeSi, VO and CrSb have no `.vesta` file and no render there, so they are supplied by hand
  and cropped in place. Either way the crop is found rather than typed in: ink is anything
  coloured or dark, its columns fall into groups with white between them, and the widest
  group is the structure. The results go into the composites at 444–882 ppi, against 200 ppi
  in the published figures.

### The four panels that had no generating script

S1, S2, S4 and Fig. 4b were assembled without a script surviving in the deposit. They now
have one each, and all four were checked against the published PDFs.

**Fig. 4b** and **S4** are ports of the cells of the working notebooks that made the
published panels — `fig_heatmap_filled` and `FIG_OPT_PROGRESS` respectively. Only the input
and output paths are changed, plus one correction in Fig. 4b: the original applies
`% mask.sum()` to two legend strings that carry no format placeholder, which raises
`TypeError` before anything is drawn, so the cell cannot be executed as it stands. The
counts it meant to print go to stdout instead. S4 reproduces the published curve exactly,
including the best-so-far steps at trials ≈28k, ≈37k and ≈43k that end at 1.0605 eV.

**S1** and **S2** are written from scratch against `data/fin_data.csv`, because no script
for them exists anywhere in the project. Both need to know which of a formula's two
elements is the magnetic one; `_cohort.py` settles that by matching the symbols parsed out
of `filename` against the tabulated `magnetic_atomic_number` / `nonmagnetic_atomic_number`,
and raises rather than dropping a row it cannot resolve. All 3,845 resolve.

S1 reproduces the published bars exactly apart from the six rows removed after that figure
was made — five `Cr2F8_cluster3` duplicates and one `Cu2O2_1_st05`:

| Panel | Published | Here |
|---|---|---|
| (a) first bin / fifth bin | 1665 / 135 | 1660 / 134 |
| (b) Cr / Cu | 625 / 116 | 620 / 115 |
| (c) MX / MX₄ | 1518 / 445 | 1517 / 440 |

Every other bar is unchanged, and the differences account for exactly those six rows. No
cell of S2 moves: none of the six held the maximum for its M–X pair.

### The published band panels are a zoom; the full path is deposited too

`BAND.dat` for CuO and FeSi holds 80 k-points over k = 0 to 2.6 - the first two segments
of the path, either side of Gamma. That is what Fig. 3d/3e plot, and it is why the CuO
panel carries two blank tick labels: the notebook labels only the middle tick, and at
`ylim = (-2, 2)` with `lw = 10` just four bands are visible.

The calculation itself ran the whole path, Gamma-X|Y-Gamma-Z|R-Gamma-T|U-Gamma-V with 280
k-points, and that file is now deposited as `BAND_full.dat` alongside it. The path and its
labels are not guessed: they are the ones the group's own gnuplot script sets, and the
segment boundaries in the data land exactly on them (1.143, 2.286, 2.924, 4.721, 6.035,
7.334 for CuO). `plot_band.py CuO_full` draws it - 30 bands over -4 to 4 eV, the range that
gnuplot script uses - and the altermagnetic pattern is legible in it: spin-up and spin-down
split along Gamma-X|Y and Gamma-T|U, and stay degenerate (drawn black) along Z|R-Gamma and
Gamma-V.

`FeSi_full` is the same for FeSi, over Gamma-X|Y-Gamma-Z|R-Gamma-T|U-Gamma-V to 7.752.
Neither full-path figure appears in the manuscript; they are deposited because the zoomed
panels cannot be checked without them.

### Fonts

Every figure here is set in **Times New Roman**, with Computer Modern for the mathematics,
as the published ones are.

Times New Roman is not redistributable, so it is not in this repository. It is looked for
at run time and, if found, registered straight into matplotlib's font manager - no
system-wide install and no font-cache clearing. Put `times.ttf`, `timesbd.ttf`,
`timesi.ttf` and `timesbi.ttf` in any one of these and every figure picks it up:

    $TIMES_FONT_DIR                          explicit override
    figures/fonts/                           beside the figure code
    ~/.fonts, ~/.local/share/fonts           the usual user font directories
    /usr/share/fonts/truetype/msttcorefonts
    /Library/Fonts, /System/Library/Fonts/Supplemental        (macOS)
    /mnt/c/Windows/Fonts, /media/sf_Windows/Fonts, C:\Windows\Fonts

On a machine without it, the order is Liberation Serif, then Nimbus Roman, then DejaVu
Serif, and each script says so on stdout. The first two are metrically compatible with
Times New Roman, so line breaks and figure sizes do not move; Liberation Serif is the
closer match in glyph shape.

**Why this is centralised in `reference_plots/_fonts.py`.** Each script used to set
`rcParams['font.family'] = 'Times New Roman'` for itself, and that is a trap: when the font
is missing matplotlib does not fall back to another serif, it falls back to **DejaVu Sans**,
and the only sign is a `findfont` warning on stderr. Six of these scripts were silently
rendering in a sans-serif. `_fonts.use()` removes that failure mode; `pdffonts` on the
output confirms `TimesNewRomanPSMT` is embedded.

### Text size

The four panels written for this deposit - SI S1, SI S2, SI S4 and Fig. 4b - and the band
structures each carry a single `FS_SCALE`, applied to every piece of text in that figure.
`FS_SCALE = 1.0` is the size the published panel used.

Every one of them is at **1.0**.

**Fig. 4b is the exception to what 1.0 means.** It sits directly under Fig. 4a in the
composed figure, placed so their axes frames are the same width, and the published panel's
own type was about a tenth smaller than 4a's - so at the published sizes the two halves of
one figure carried two different type sizes. `FS_MATCH` restates 4b's sizes as Fig. 4a's,
converted to this panel's frame: 4a sets its axis labels, tick labels and colorbar label at
15 / 13 / 12 pt scaled by `FS4_SCALE = 1.54` on a 281.4 pt frame, and 4b's frame is 278.0 pt,
so `FS_MATCH = 1.54 x 278.0 / 281.4`. The composite then scales 4b by 281.4 / 278.0 and the
two panels land on the same point sizes - measured on the output, 23.09 / 20.01 / 18.47 pt
against 4a's 23.10 / 20.02 / 18.48. The published sizes were 20 / 18 / 18 / 16.

Both of 4b's axes are also pinned to 0.2 steps. At the larger tick labels matplotlib thins
the abscissa to 0.00 / 0.25 / 0.50 / 0.75 / 1.00 on its own, which leaves the two axes of
one square panel on different steps.

The SI panels are set to reproduce the published ones, and the canvas of each is chosen so
that the cropped output lands on the published page size: S2 comes out 361 x 414 pt against
the published 362 x 414, S4 425 x 281 against 432 x 288. S1 is drawn 6.0 in wide against the
published 4.0. At the published width the 18 element labels of panel (b) run together
(`CrMnFe`, `NbMoRu`) and the 10 subscripted composition labels of panel (c) collide
outright (`MX4M2X3`, `MX5M2X13MX9`) at 11 pt. Rather than shrink the text below the
published size, the canvas is widened and the text left alone; panel (c) alone takes its
tick labels to 0.9 of the rest. Each panel's y limit also clears the count printed above
its tallest bar - at `ylim = 1800` the 1660 of panel (a) ran into the frame.

Raising `FS_SCALE` does not just enlarge the glyphs, so the layout adapts to it. Past
`FS_SCALE > 1.3` (the `CROWDED` flag) S1 sets its 18 element labels, its 10 composition
labels and its panel-(b) bar counts vertically, thins the y ticks and grows the canvas;
S4 moves its three-entry legend to a band of its own above the data and raises `ylim` to
make room; Fig. 4b shortens its legend labels to `p/d < 1` / `p/d >= 1`, scales the legend
more gently than the rest and halves the colorbar label padding. S2's canvas scales with
`FS_SCALE` throughout, because 414 annotated cells cannot hold more text at a fixed size.

Fig. 2, Fig. 3a-c, Fig. 4a and SI S3 keep their own scales (`FS3_SCALE`, `FS4_SCALE`),
which were set separately.

### Output resolution

Two numbers, applied the same way by the notebook and by `reference_plots/_save.py`:

| | PNG | PDF |
|---|---|---|
| Fig. 2 | 1000 dpi | rasterized layers at 400 dpi |
| everything else | 800 dpi | rasterized layers at 400 dpi |

In a PDF the text, axes and lines are always vector; `PDF_RASTER_DPI` governs only the
`rasterized=True` layers - the point clouds - and a figure with none is unaffected by it.
SI S1, SI S3 and the two band structures are entirely vector, so their PDFs carry no image
at all; SI S2 and SI S4 embed one each, Fig. 4b two. 400 dpi is above the 300 dpi journals ask
for raster content and costs a third of the memory of rendering the PDF at 800.

### Memory

These figures are large and the pipeline is meant to run on a modest machine, so the memory
cost was measured rather than guessed. For Fig. 3a-c (5.4 x 11.4 in), peak RSS of the whole
process:

| Step | Peak |
|---|---|
| building the figure | 0.10 GB |
| writing the png at 800 dpi | 0.45 GB |
| writing the pdf at 800 dpi | **1.18 GB** |
| writing the pdf at 400 dpi | 0.39 GB |

The PDF dominates because the scatter layers are `rasterized=True`, and matplotlib renders
each of them into a full-canvas buffer at the save dpi before embedding it. Dropping only
that resolution to `PDF_RASTER_DPI = 400` - still above the 300 dpi journals ask for raster
content, and with every line and glyph still vector - brings the peaks down to:

| Figure | Before | Now |
|---|---|---|
| Fig. 2 (1000 dpi png) | 1.10 GB | **0.72 GB** |
| Fig. 3a-c | 1.29 GB | **0.55 GB** |
| SI Fig. S3 | 0.50 GB | **0.36 GB** |
| Fig. 4a | 0.34 GB | **0.30 GB** |
| SI Fig. S2 | 1.11 GB | **0.31 GB** |

SI S2 was separate: `imshow` resamples its 23 x 18 array up to the whole canvas, which on
a 16.8 x 16.0 in figure is 1 GB and bakes the cells into a bitmap. `pcolormesh` draws the
414 cells as vector quads instead - a third of the memory, a PDF twenty times smaller, and
crisp cell edges at any zoom. `reference_plots/_save.py` gives those scripts the same
measure-the-crop-box-once treatment the notebook uses.

The PDFs shrank with it - Fig. 2 from 1.1 MB to 0.35 MB - and the run got faster. The crop
box is also measured once at 100 dpi and reused, instead of letting `bbox_inches='tight'`
re-render the canvas at full dpi for every output file, and `save()` closes the figure when
it is done.

`make_all_figures.py` runs each generator in its own subprocess, so no two peaks overlap:
the whole set now needs about 0.8 GB free, not 1.4 GB. If one is still killed, the run
reports `SIGKILL - almost always out of memory` and you can re-run just that panel with
`--only`.
